DeltaDOM はブラウザが観測した内容を記録し、ステップ間の変化を比較し、過去の観測をオフラインで復元することもできます。自動操作の確認、誤クリックの調査、動的なページの変化の保存に使えます。

**0.4 は実験版です。** Apple Silicon Mac でコンパイル不要のインストールを確認しています。デモには API キー、モデルのアカウント、プログラミング経験は不要です。リンク先のガイドの多くと一部の CLI メッセージは、現在中国語です。共通のアニメーション内の字幕は英語です。

### ローカルプレビューを開く

ローカルで提供された **DeltaDOM-0.5.0.dev9-macosx_11_0_arm64.zip** を展開し、**Start DeltaDOM.command** をダブルクリックします。ビルド済みのプログラムをインストールし、実際のブラウザでデモを開きます。モデルのアカウントは不要です。この ZIP は GitHub Releases に掲載されていません。下記の旧版には新しい試作機能は含まれません。

新プレビューのフォルダで、自分のクリック対象を保存できます。`https://example.com` を操作したいページの URL に置き換えてください。

```sh
python3 run.py bind https://example.com --output action.json
python3 run.py bound-click action.json
```

最初のコマンドでは、Option/Alt キーを押しながらクリックして対象を選びます。次のコマンドでは、保存した識別情報に合う対象へ実際のクリックを 1 回送り、確認できるようブラウザを開いたままにします。識別情報の変化を検出すると操作を止めます。自動再試行はせず、クリックできたことを業務処理の成功とは見なしません。[詳しい使い方](docs/BINDING-PREVIEW.md)。

通常の並べ替えでは、281 個のボタンで V9 と強力な単純ベースラインである文脈確認方式が同じ結果でした。固定した 11 個の入力シナリオを、通常のハンドラーと信頼された入力を必要とするハンドラーで別々に検証したところ、Browser Use の標準クリックとクリック直前の手動確認では、それぞれ各ハンドラー種別で 6 シナリオに誤った作用が生じました。V9 では各 2 シナリオでした。これはタスク全体の成功率ではありません。[検証手順、強いベースライン、すべての反例と結果](benchmarks/BINDING-V9-RESULTS.md)。

## 旧版 0.4：観測の記録

1. [Mac 向けプレビューをダウンロードして展開](https://github.com/Eman0n911/deltadom/releases/download/v0.4.0/DeltaDOM-0.4.0-macosx_11_0_arm64.zip)します。Python 3.12 以上（または uv）と Google Chrome が必要です。
2. **Start DeltaDOM.command** をダブルクリックするか、展開先で `python3 install.py` を実行します。
3. 実際のブラウザがフォーム入力、一覧の並べ替え、商品選択、再読み込みを行います。ターミナルに **Verified 8/8** と表示されることを確認してください。

Rust、Node.js、コンパイラーは不要です。初回は依存パッケージをダウンロードします。デモがアクセスするのは同梱のローカルページだけです。困ったときは[インストールガイド](START_HERE.md)を参照してください。単体のデスクトップアプリではなく、署名・公証もされていません。

```text
STEP                   FRAME   NODES  FULL BYTES  SENT BYTES  CHECK
initial                full      304      32,556       7,203  OK
unchanged              delta     304      32,556          76  OK
fill                   delta     304      32,560         117  OK
reorder                delta     304      32,576         638  OK
same_url_reload        full      304      32,556       7,203  OK
```

これは 0.3 の取得処理を使った実際のデモ出力の抜粋です。0.4 は同じ符号化方式を引き継ぎ、検証可能な記録ファイルを追加しています。[当時の出力全文](artifacts/preview-demo-0.3.txt)。数値はローカルの例におけるバイト数で、モデルの利用料金ではありません。

## 何が変わったかを調べる

デモの後、展開先のフォルダで次のコマンドを実行します。

```sh
# ブラウザを起動せずに記録の整合性を確認
python3 run.py replay deltadom-output/demo.ddt

# フォーム入力前後の観測を比較
python3 run.py diff deltadom-output/demo.ddt --before 2 --after 3

# ステップ 3 を読みやすい JSON として復元
python3 run.py replay deltadom-output/demo.ddt --step 3 --output step-3.json
```

自分のページを記録するには：

```sh
python3 run.py record https://example.com --count 30 --output example.ddt
```

別に開いたブラウザで操作すると、DeltaDOM が毎秒記録します。記録はローカルに保存されますが、ページやフォームの非公開情報を含む場合があるため、共有前に確認してください。普段のブラウザのログイン済みプロファイルは読み込みません。既存の記録ファイルや書き出し先は上書きしません。[記録、中断時の復旧、連携](docs/RECORDING.md)。

## 既存のエージェントに記録を追加する

wheel をインストールした Python 環境で、既存の Browser Use のモデルと操作ロジックをそのまま使えます。

```python
from deltadom import BrowserUseRecorder

with BrowserUseRecorder("agent.ddt") as recorder:
    await agent.run(on_step_end=recorder.on_step_end)
```

このコールバックは Browser Use **0.13.11** で検証しています。各ステップの終了時に、最後のモデル入力、出力、操作結果を記録します。モデル入力は変更せず、プロバイダーへのすべてのリクエストや再試行を記録するわけでもありません。非公開の MessageManager フィールドに依存するため、更新後は再検証が必要です。[インターフェースの範囲](docs/RECORDING.md#接入已有-browser-use-智能体)。

Playwright では、`DeltaBrowser` が意味情報を持つノードの差分、安定 ID による操作、明示的に許可した API フィールドの読み取りにも対応しています。[SDK](docs/SDK.md) · [サンプル](examples/observe.py)。

## 測定結果

| 比較 | 結果 | 適用範囲 |
|---|---|---|
| 同一の Browser Use 出力をフレーム単位で保存 | **48.7%–59.1% のバイト数削減** | 既存のページ記録で、各フレームを独立に zlib 圧縮し、同等の整合性検査を加えた場合との比較 |
| 元の内容の復元 | **450/450 がバイト単位で一致** | 3 種類の観測元、それぞれ 150 スナップショット |
| セッション全体の gzip アーカイブ | **gzip のほうが小さい** | 終了後のバックアップだけが目的なら gzip が適しています |
| モデルの利用料金とタスク全体の成功率 | **改善は実証されていません** | 記録コールバックはモデル入力を変更しません |

[検証手順、全結果、否定的な結果](benchmarks/RECORDING-RESULTS.md)。以前の公開ページでの観測層比較では、agent-browser 標準の差分がより短く、Browser Use 標準の DOM 取得がより高速でした。保存容量の削減だけでは、ブラウザエージェントより優れているとは言えません。

## どのツールを使うか

- AI に Web 上のタスクを自律的に実行させたい場合：[Browser Use](https://github.com/browser-use/browser-use)。
- ターミナルからブラウザを操作したい場合：[agent-browser](https://github.com/vercel-labs/agent-browser)。
- ページの増分記録、フィールド単位の比較、検証、観測の復元を行いたい場合：既存のツールとともに DeltaDOM を試せます。

記録形式は、前のフレームを辞書として標準の zlib を使います。検証、増分記録、復旧を組み合わせた点に用途があります。新しい圧縮アルゴリズムではありません。また、他のツールに再生機能がないと主張するものでもありません。これらのプロジェクトとの提携関係はありません。

## 対応範囲と制約

- V9 はクリックを 1 回ずつ保存・再実行する仕組みで、タスク全体を計画しません。現在はトップレベルの一般的な HTML コントロールに対応し、保存時と完全に同じ URL を必要とします。検出できない変化もあり、先に実行されたハンドラーの副作用を取り消したり、サーバー側の業務処理の成否を確認したりはできません。
- 正確な復元の対象は取得した意味情報を持つノードや元のテキストです。完全な HTML、動画、ブラウザ状態ではありません。Playwright による取得は iframe の内部、閉じた Shadow DOM、canvas の画素を含みません。
- ページ観測には既定で 60 ms の安定待ち時間があります。不安定な状態は報告できますが、その後ページが変化しない保証はありません。
- 1 ステップの記録上限は 16 MiB です。履歴や base64 のスクリーンショットを含むメッセージ配列は、通常の利用でも超過することがあります。その場合、`BrowserUseRecorder` はステップ番号、メッセージ数、バイト数を記した省略レコードを保存し、エージェントを中断しません。再生時の `omitted_snapshots` が省略数を示し、省略した内容は復元できません。その他の書き込み・シリアライズのエラーは引き続き送出されます。破損した記録は検証に失敗します。`replay --recover` は中断した記録の先頭から検証できた部分を復元し、不完全と明示します。整合性ハッシュは出所の真正性を証明しません。
- Mac arm64 向けプレビューはローカルでインストールと動作を確認しています。他の環境でソースやビルドを確認したことは、その環境向け配布パッケージのインストール検証を意味しません。
