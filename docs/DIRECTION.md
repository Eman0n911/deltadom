# 当前决定：保持私密，先证明可靠性价值（2026-10-22）

GitHub `Eman0n911/deltadom` 已按所有者要求设置为 **Private**。0.4 曾公开发布是历史事实；代码、标签和附件保留在私密仓库。后续恢复公开必须得到所有者新的明确授权。本轮研究与诊断留在本地，不发布新版本。

当前没有足够证据说明 DeltaDOM 有强创新或端到端竞争优势。0.4 的安装和记录功能能运行，但工程完成不等于产品成立。此前将标准压缩与回放组合当作发布依据，判断过早。

本轮已实现结果核对原型并完成真实模型试验。统一配置的购物干预回合中，链接候选成功用了 19 次中继请求，简单核对 17 次、agent-browser 16 次；未证明优势。官方评分还存在同价 SKU 歧义，不能拿原生分支的那次评分失败宣传胜出。完整冻结集合没有跑完，旧候选已因自身限制被否决；保留全部原始输出。见[本轮结论](../benchmarks/OUTCOME-RESULTS.md)。

## 先否决哪些方向

- 不再以 Rust、更短 DOM、增量或 zlib 字典压缩为核心卖点。已有实测中，公开页面的原生观察基线更强；模型费用收益没有证据。
- 缓存与自愈不是空白市场：[Stagehand 缓存文档](https://docs.stagehand.dev/v3/best-practices/caching)已经描述页面内容相关的缓存和本地重放。[agent-browser](https://agent-browser.dev/diffing)已有状态差分。
- 执行前验证也不是新概念：[Atomicity for Agents](https://arxiv.org/abs/2603.00476)研究观察到执行之间的状态变化及校验防护。仅加 MutationObserver 或“变化就停”不能声称原创。
- 按需观察已有[Signal-Driven Observation](https://arxiv.org/abs/2606.06708)；任务前后条件已有[Web verbs](https://arxiv.org/abs/2602.17245)论述。组合这些概念也不自动成为强创新。

本轮做了 32 次真实浏览器诊断。旧实现会在相邻订单/金额已变化后继续点击；但整页、整行校验都比人工语义定位误拦更多，因此否决作为默认方案。见[协议与全部负结果](../benchmarks/IDENTITY-RESULTS.md)。这是我们实现的缺口，**不能据此声称主流工具也有同样失败**。

## 唯一优先验证的产品假设

**让现有浏览器智能体办完事后，能核对对象和结果，并把没有确认的部分明确告诉使用者。** 首先只做批量记录修改、表单保存两类流程；从可复位的本地邮件/业务系统开始，不接管真实支付或真实用户消息。

使用者说“把这五条记录改成已处理，不动其他记录”。候选系统应能：

1. 从任务与可见页面提出待核对的对象和条件，而不是让使用者填写 CSS selector 或 JSON。
2. 操作前核对仍是同一业务对象；无关计数器变化不应阻断。同名、缺少身份字段时保留歧义，不能凭位置猜。
3. 操作后通过网站正常提供的重新读取路径检查对应记录。按钮点击成功、toast 或 HTTP 200 都只算操作迹象；新的独立读取也要检查实体、字段和新鲜度。没有可用证据就输出“尚未确认”。
4. 只对明确未执行且可安全重试的步骤自动重试；“可能已经提交”不能盲目重放。界面中显示“5 条中 4 条已核对，1 条需确认”和证据入口，而不是显示一串 DOM 指标。

以上完整产品行为仍未实现；本轮已落地可见字段核对、记录成员核对及对象链接身份核对，并接入真实 Browser Use / agent-browser 模型循环。现有原型只提供局部页面证据，未解决完整任务条件生成，也没有竞争优势证据。见[原型](OUTCOME-PROTOTYPE.md)和[全部原始试验](../benchmarks/OUTCOME-RAW-RESULTS.md)。DDT 只保留为内部调试记录。候选技术价值在于：自动生成与维护任务相关的核对条件、用少量额外读取选择足够证据、跨页面变化保持对象绑定。能否比普通定位、重读、提示词和现有框架好，必须实验；目前不声称学术首创。

## 怎么让竞争判断可以被推翻

主要公开评估候选选 [BreakingWeb](https://github.com/Arvid-pku/BreakingWeb)。其[论文](https://arxiv.org/abs/2609.35814)提供正常/干预成对任务，并按最终后台状态评分，包含假成功、保存漂移等问题。论文结果不是我们的结果；已运行邮件开发任务及冻结集合首项购物任务的小规模真实模型回合；完整固定集合仍为 **not_run / incomplete**，不能称为全基准成绩。它比继续比较自建表格 token 更接近上述产品目标。WebArena/BrowserGym 可作为后续跨环境检查，但不同时铺开全部环境。

本地只读源码预检已完成：上游 `052f0f0c6cfcdc9efb86eb0183556fcc4fb3606e`，519 个任务 YAML、535 个干预 YAML，覆盖 7 个目录；[预检记录](../artifacts/benchmarks/breakingweb-preflight.json)。环境未安装、评分器未运行、没有模型成绩。上游源码独立放在忽略目录，未并入或分发本项目；任务配对选择不能直接把 535 个配置当成论文中的 519 对。

先固定上游版本、任务清单和划分，再运行候选。开发集用于排错，确认集包含未调优的网站与变化类型。评分器和后台真值只能由实验控制器访问，候选只拿到与基线相同的任务和正常浏览器证据。不能给候选评分函数、最终答案、私有 API 或更长预算。

同一模型、同一 actor、同一工具权限，至少比较：

| 分支 | 目的 |
|---|---|
| 原生 agent | 现有行为 |
| 原生 agent + 明确要求重新打开记录核对 | 排除只是提示词有效 |
| 原生 agent + 简单结构化条件/重读检查 | 最强廉价基线；人工指定条件须单独标记，不能冒充自动能力 |
| 原生 agent + 候选自动核对 | 检验新增机制 |

再与 Stagehand、agent-browser 的原生流程比较；框架间比较是整体产品表现，不能单独归因于某个感知算法。现有 API、缓存、自愈功能必须保留。不能让对手用脆弱位置选择器，而候选得到人工任务语义。

共同报告真实完成率、错误修改数、假成功数（全部任务分母及声称成功分母）、有条件可完成却放弃数、人工介入数、完整耗时和实际模型用量。不能靠一律拒绝降低错误，也不能把合成诊断算成模型得分。

第一轮是可行性门槛，不是发布门槛：候选必须比最强简单基线少报假成功，且完成率不降低；如只会更保守地拒绝或依赖逐站人工选择器，就停止该路线。再在独立任务上验证，报告配对差异和区间；证据不足就扩充固定批次或保留“未证明”，不挑样本。费用/速度优势只有实际完整上下文与 usage 能测到时才报告。

资源边界：本轮只做本地、无模型费用的诊断。用户指定的 ChatGPT Desktop 三模型、WorkBuddy 渠道保持不变；Desktop 受限时记 `not_run`，不用 SpineCodex 或付费 API 替代。大批模型实验的任务数量与总预算需在运行前按真实渠道能力确定，不能承诺尚无能力完成的批量跑分。

## 大众化的顺序

先用上述测试证明收益，再做“选择流程 → 看待处理记录 → 运行 → 查看已核对/失败/待确认”这条短路径。保留免编译安装与真实浏览器演示，视觉沿用常规 GitHub README、简洁截图和原生浏览器，不新建营销 HTML。公开前还需至少一次目标使用者独立安装和完成任务的观察；开发者自己跑通不算非专业用户验证。

公开门槛：有独立任务上的真实收益、负结果与边界公开、普通用户路径可完成，并得到所有者明确发布授权。**本轮只完成私密化、候选否决实验与下一方向决策，没有完成新产品或强创新证明。**

# DeltaDOM 的竞争方向（2026-10-22）

## 当前结论

0.3.0 修复了已复现的操作缺口，改进了可重建编码，但不是通用 Browser Use / agent-browser 替代品。原生 agent-browser 已有增量，Rust、增量、表格折叠都不能单独构成优势。发布前应先建立一种稳定、可重复、对使用者有价值的胜出场景。

实测边界见 [0.3 报告](../benchmarks/RESULTS-v2.md)：自建列表较 agent-browser 增量节省 11.5% 新输出；公开页面开发集和未调优页面仍落后。观察调用也更慢。模型输入历史、缓存后费用和正式成功率未得到验证。不要把自建样例胜出外推到任意网页。

## 有根据的切入点

把目标收窄为**给现有浏览器智能体提供可重建的状态更新**。优先验证重复列表、长表格、多步骤筛选和局部状态变化。现有代码已经具备稳定 ID、字段/属性差分、可重建文本、丢帧检测和更新前目标核对；这些是工程能力，不是已证明的独占能力。

0.3 的改进让这个方向可测试：模型只需看到改变的字段；接收方可以独立恢复完整捕获结果，导航/丢帧后请求全量。短小静态页面可能完全不需要它，应允许原生观察直接通过，避免让所有请求承担额外成本。

## 怎样证明超越

1. **先做原生观察适配。** 接入同一个 Browser Use actor/action loop，固定原来的节点引用与动作接口。A 组用原生完整观察，B 组只改变观察传递方式。不要同时换感知算法、模型、动作工具和提示词，然后把差异归因于压缩。此集成尚未完成。
2. **以实际发送内容为准。** 记录每步提交给模型的完整上下文、缓存 token、输出 token、费用、重试和结果。保留全部历史差分可能让总输入持续增长；所以需要测量“最近完整状态 + 有界更新历史”的重建/压缩策略，而非只加总新输出。
3. **把正确性设为门槛。** 新测试集预先登记，开发集与确认集分开。先要求任务成功率不劣（预先选定容忍差值和样本量），再评估费用/完成耗时是否下降。没有 provider usage 时只能报告代理指标。
4. **拆开优化等待与捕获。** 当前约 60 ms 的稳定窗口是一项明确策略。直接跳过它已触发定时更新回归，候选被拒绝。未来可由现有 actor 共用一次稳定判定，避免双重等待；必须通过延迟网络、动画、导航和定时器测试后，才能计为速度收益。
5. **再验证 API 数据路径。** 只对显式许可的响应字段，比较“DOM 扫描多页”与“已收到的结构化响应辅助观察”。必须证明数据和任务目标对应，不能用隐藏答案、任意端点爬取或越权数据制造胜出。

首个对外承诺应形如：“在预登记的动态列表任务、同一模型及 actor 下，保持成功率，降低实际输入费用 X%”。现在没有足够证据填入 X；不以愿景代替测量。

## 继续投入与停止标准

先完成上面的同 actor 适配及固定小批闭环。如果成功率下降、缓存抵消收益或优势只存在于自建商品页，就收缩为状态同步/回放库，或停止将其定位为通用 agent 加速器。保留负结果，不换一组样例继续追宣传数字。
