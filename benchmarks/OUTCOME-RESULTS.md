# 结果核对原型：实现了，但没有证明竞争优势

本轮保留 **16 次运行尝试**，其中 15 次进入真实模型决策、1 次在 CLI 初始化失败；共 177 次桌面中继请求，包括超时、无效输出及工具内部的提取请求。不能把这些不同版本、不同阶段的回合合并为一个成功率。GitHub 继续保持私密，本轮没有推送或发布。

## 最有判别力的一组结果

任务是冻结清单第一项 `amazon_browse_category`，干预是事先选定的 `amazon_browse_category__cheapest_decoy.yaml`。四个分支在独立网站会话和独立 WorkBuddy 会话中运行，使用同一 Deepseek-V4.1-Flash 桌面通道、相同源码绑定、40 个动作预算单位、600 秒单次中继等待及 2400 秒回合上限。此时正常条件已用于诊断，所以这一组明确是**探索性对比**。

| 分支 | 官方成功 | 模型声明 | 中继请求 | 动作预算单位 | 记录 |
|---|---|---|---:|---:|---|
| Browser Use 0.13.11 原生循环（限制为 UI 操作） | 否 | 成功 | 13 | 13 | [e001](../artifacts/benchmarks/outcome-v1/e001/result.json) |
| 同一循环 + 简单重读核对指令 | 是 | 成功 | 17 | 16 | [e002](../artifacts/benchmarks/outcome-v1/e002/result.json) |

候选没有超过简单核对和 agent-browser。本组各一次，不能形成统计优势结论；请求数不是全部 WorkBuddy 内部生成次数，也不是 token、费用或推理速度。任务有交叠运行，桌面排队和传输等待也使总耗时不能用于速度排名。候选曾被 WorkBuddy 的重复操作提醒暂停，在既定预算内恢复一次，未添加任务提示、未改变权限设置，见[记录](../artifacts/benchmarks/outcome-v1/e003/desktop-intervention.json)。

### 官方评分还存在任务歧义

结束并封存四个模型回合后才读取该干预配置。它新增三件同为最低价 $7.99 的商品；用户任务只要求“最便宜的可购买商品”，评分却只接受原始 SKU。e001 选择了并列最低价的另一个 SKU。因此其官方失败**不能直接等同于字面用户任务失败**，更不能用来宣传候选胜出。保留原始评分，不删掉这条样本，也不把它换成更有利的案例。详见[语义审计](../artifacts/benchmarks/outcome-v1/semantic-audit.json)和[固定版本的上游配置](https://github.com/Arvid-pku/BreakingWeb/blob/052f0f0c6cfcdc9efb86eb0183556fcc4fb3606e/breakingweb/injector/variants/amazon_browse_category__cheapest_decoy.yaml)。

该配置还让前两次加购写入静默失败。部分模型在第三次尝试前设置数量为 1，随后推断“数量没设置导致失败”。这没有因果证据；从注入定义看，不能把第三次写入成功归因于数量操作，更不能宣传原型自动诊断出了数量问题。

## 原型迭代和失败没有隐藏

- 邮件开发任务：原生循环未完成且诚实报告失败，10 次请求；简单核对成功，9 次；agent-browser 成功，7 次。
- 字段契约 v1：后台目标已实现，但模型输出失败，18 次请求，未形成可用完成结果。v2 也实现了后台变更，却因错误属性预期和冻结条件报告未确认，18 次请求。
- 文本身份成员核对 v3：邮件开发任务成功，12 次请求、14 个预算单位，仍落后于强对照。冻结购物任务的正常条件中，它把排序误判为业务写操作，禁止注册契约，最终失败。该候选被否决，没有换样本挽救成绩。
- 链接身份核对 v4：修复了上述交互限制，用已观察的 URL 与可见名称绑定对象，不再要求不同页面恰好展示相同两段文本。购物正常条件的开发复验成功，8 次请求、9 个预算单位。这个修复结果没有替换 v3 的失败，也没有冒充未见确认成绩。

完整逐回合表和剩余 `not_run` 在[原始汇总](OUTCOME-RAW-RESULTS.md)。完整的 7 环境 × 2 条件 × 4 分支确认尚未完成；首个正常任务的早期对照还经历了超时配置修正，不能声称已经完成合格确认，更不能报告整个 BreakingWeb 的成绩。

## 已修复的具体问题

1. agent-browser 会话名过长导致 macOS socket 启动失败；改为短唯一名称并保留原始失败。
2. CLI 脚手架遗漏下拉选择、勾选、键盘和字段读取能力；补齐后用真实 CLI 验证，避免削弱对照。
3. Browser Use 的内部 90 秒超时早于中继的 600 秒；显式统一后续回合。旧回合及其空缺回复不改写。
4. 读取结果页后，必须走 Browser Use 导航接口同步节点缓存；记录原始节点引用错误。
5. 任意排序动作不能让成员核对永久不可用；新链接版在相关变更之前建立当前基线。
6. 重复身份、同名不同链接、已有成员、跨域读取、核对期间收到失效通知、准备失败后残留旧证据等边界已覆盖。

另有一处已独立复现的数据传递缺口：已安装且与 wheel 记录一致的 Browser Use 0.13.11，在工具同时给出完整 `extracted_content` 和简短 `long_term_memory`、但未设置一次性读取标记时，下一轮只收到摘要。原生回合确实留下了“找到 23 条结果”，完整结果未进入实际请求。`deliver_read_evidence` 保留短记忆并把完整读取送入下一轮；通过原生 MessageManager 的构造验证。见[审计](../artifacts/benchmarks/outcome-v1/read-result-delivery-audit.json)。**这是上下文构造修复，不是模型成功率提升证据；当前冻结模型组未启用此修复。后续若做正向归因，强对照也必须同样修复。**

## 交付和判断

[SDK 原型与运行入口](../docs/OUTCOME-PROTOTYPE.md)已可用；全部 Python 测试 **39 通过**，修改的 Python 文件通过 Ruff，新增 CLI 能力及原生消息构造各自有独立验证。上游 BreakingWeb 任务、干预、评分源码未改动。真实模型只使用 WorkBuddy；ChatGPT Desktop 的 GPT6.1Sol / Luna / Astra **not_run**，没有擅自换成 API 或 SpineCodex。

这版只证明可以生成局部、可核查的页面证据。它没有证明自动恢复、任务完整性或相对强对照的优势。扩大同一候选、继续调整重试次数去适配已知注入，无法补上这个缺口。因此本轮不扩展为产品发布，不挑更容易的样本宣布胜出；保留可运行组件、全部负结果与未完成项。
