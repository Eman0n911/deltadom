# 恢复与请求防重放：发现一项窄机制收益，尚非竞争性产品

本轮先否决“持久化对象锁就是创新”的解释，再实现浏览器请求转发防重放。
已有可运行组件及无模型验证。没有把减少核对步骤作为新贡献；没有修改原 BreakingWeb
样本、干预或评分器，也没有把本轮合成故障加入它的成功率分母。

## 强简单核对的实际缺口

读取不到结果不能区分“根本没提交”与“提交了但 UI 还没显示”。按模型动作 ID
写日志也挡不住重新规划产生新 ID。更进一步，**动作回调只执行一次，网页自己的
脚本仍可能发送两次请求**。最后一个缺口发生在工具调用日志以下，V7 自身也失败。

这一方向不是从分布式系统文献中未曾出现的问题。参考
[AWS 重试与幂等 API](https://d1.awsstatic.com/builderslibrary/pdfs/making-retries-safe-with-idempotent-apis-malcolm-featonby.pdf)
与 [Temporal 术语说明](https://docs.temporal.io/glossary)。本项目只声称实现和实测过下面的浏览器适配。

## V7：对象锁有用途，但与强简单实现打平

预先固定 [12 个故障场景](../artifacts/benchmarks/recovery-v7/protocol.md)，每种场景四个分支，
每格一次原始尝试、最多一次明确恢复调用，保留全部 48 格。故障包括进程状态丢失、
延迟 UI、并发、改 ID、改绑定、迟到读取、读失败和取消。它们是人为构造的开发反例，
不是 12 个独立真实任务，也不用于统计显著性判断。

| 方案 | 额外副作用次数 | 错误 ID 绑定放行 | 迟到证据误确认 | 预定副作用数量正确的格数 |
|---|---:|---:|---:|---:|
| 每次操作前精确核对 UI | 4 | 1 | 1 | 7/12 |
| 持久化请求 ID 日志 + 精确核对 | 3 | 0 | 1 | 9/12 |
| 独立编写的对象锁 + 版本核对简单基线 | 0 | 0 | 0 | 11/12 |
| V7 RecoveryLedger | 0 | 0 | 0 | 11/12 |

最后一列只统计效果数量，不包含证据正确性；应与前几列一起看，不能称作任务成功率。
最强简单基线保留了互斥、不可变绑定、版本检查和同等 UI 核对，候选没有隐藏额外信息。
V7 与它打平，因此**不把 V7 当作独有竞争优势**。二者都在“实际未执行但结果不明”一格
留下未决任务，不能靠拒绝一切宣称成功。

[正式诊断原始结果](../artifacts/benchmarks/recovery-v7/fault-r2/result.json)。r1 缺少协议要求的
基线前置核对，结果保留但不采用；修正后重新运行完整 48 格，没有挑格或换样本。

额外的真正子进程退出测试覆盖：准备后退出可恢复；写许可落盘后、发出前退出会保守阻断；
副作用发生后退出也不会再发。不是用重新构造 Python 对象冒充全部崩溃验证。

## BreakingWeb：16 格真实 UI 集成，不是模型成绩

使用原先已经参与开发的 Gmail star、Amazon category/cart，固定 seed 42、原始正常/干预
配对，四分支共 16 格。每格真实点击一次后，注入调用方丢失确认，再用新动作 ID 恢复一次。
原文档和 URL 均保留，临时读取页关闭。

- 正常条件：全部 8 格读取到对应目标，四个方案均只执行 1 次点击。
- 干预条件：全部 8 格未读取到目标。普通核对和请求 ID 日志各执行 2 次点击；对象锁和
  V7 各执行 1 次。没有提高重试次数去跨过已知干预门槛，也没有把少写一次算作成功。
- 16 格均完成执行，无组件错误。**V7 在这组检查没有完成率优势**。

[全部记录](../artifacts/benchmarks/recovery-v7/browser-r1/result.json)。这只是脚本化组件集成，
没有调用模型、没有运行官方任务评分器。原 7 站 × 2 条件的自主任务集合仍未完成。

## V8：将防重放移到实际请求转发处

`NetworkFence` 在路由转发前将请求精确摘要落盘。保护的是同一意图下同一方法、URL、
正文原始字节的再次发送；不读取响应正文，不假造成功回复，不改变页面的原始请求内容。
普通 SQLite 对象锁只管回调执行次数，管不到回调中网页脚本的网络重发。

预先固定 [8 场景 × 4 分支](../artifacts/benchmarks/recovery-v8/protocol.md)，用真正的
Chrome 和本地 HTTP 服务执行，服务端记录实际收到并执行的请求，组件不读取服务端计数。
普通 Playwright、V7 对象锁、内存请求去重、V8 持久请求去重共 32 格全部执行。

| 场景 / 预定效果数量 | Playwright 单回调 | V7 对象日志 | 内存请求去重 | V8 持久请求去重 |
|---|---:|---:|---:|---:|
| 一次正常提交 / 1 | 1 | 1 | 1 | 1 |
| 页面并发发出相同请求 / 1 | 2 | 2 | 1 | 1 |
| 服务端提交后丢失回复、页面再发 / 1 | 2 | 2 | 1 | 1 |
| 新浏览器上下文恢复页面后自动重发 / 1 | 2 | 2 | 2 | 1 |
| 两份不同正文的合法操作 / 2 | 2 | 2 | 2 | 2 |
| 语义相同、JSON 排版不同 / 1 | 2 | 2 | 2 | 2 |
| 本来需要两份相同请求 / 2 | 2 | 2 | **1，误拦** | **1，误拦** |
| 307 原端点与跳转端点均有副作用 / 1 | 2 | 2 | 2 | 2 |

表格为服务端实际效果次数。每格的 actor 回调恰好一次；“恢复页面自动重发”没有第二个
工具回调，所以对象日志无法干预。效果数量符合预定值的格数为 **3、3、4、5 / 8**。
不是模型成功率。V8 对内存对照的增益只有跨上下文恢复这一格，不能放大成通用性能结论。

[全部请求轨迹、来源源码和结果](../artifacts/benchmarks/recovery-v8/network-r1/result.json)。
内存对照与候选共用相同路由处理，只移除持久化，属于机制消融。这里的 Playwright 单回调
不是 Browser Use、Stagehand 或 agent-browser 的完整自主任务运行，不能据此排列这些产品的名次。

32 格无执行错误。保留两个漏拦和一个误拦，不能选择前三个有利故障单独宣传。
这是范围明确的机制收益，不是证明强学术创新，也没有证明胜过具有相同持久转发机制的系统。

307 与 Service Worker 的范围限制与
[Playwright 路由文档](https://playwright.dev/python/docs/api/class-browsercontext#browser-context-route)
一致。指纹不同就视作不同请求，没有依据某个测试后端的解析规则偷偷归一化正文。

## 采用决定与成本

- V7 保留为可选恢复基础设施，与强简单基线打平，不作为核心创新卖点。
- V8 仅作为**明确不允许同一精确请求重复提交**的专用流程原型；不默认加入所有浏览器动作。
  合法重复请求、字节变化、重定向等反例决定它还不能成为通用保护层。
- 自然语言目标到稳定业务对象、合法重复次数/幂等语义的自动识别仍未解决；示例提供的
  人工资源键和操作定义不能冒充自动能力。
- 本轮无模型调用，模型费用为 0。用户已授权付费；没有把额度当作停工理由。
  在限定范围和误拦问题解决前，付费自主任务分数难以区分机制作用，因此没有消耗积分。
- 没有发布或推送；未更改 GitHub 可见性。保留原私密状态，不恢复公开。
