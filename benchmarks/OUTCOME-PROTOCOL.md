# Outcome v1：原型与固定对照

范围：私密本地实验，无付费 API、无公开发布。使用所有者已指定的 WorkBuddy Deepseek-V4.1-Flash。通过独立会话读取原生请求、写回原始 JSON，不由实验控制器替模型选动作，不修补模型输出。每回合新浏览器与新网站 session，评分只在模型结束并封存结论后进行。

## 样本冻结

[manifest.json](../artifacts/benchmarks/outcome-v1/manifest.json) 在实现原型前生成。上游 BreakingWeb `052f0f0c6cfcdc9efb86eb0183556fcc4fb3606e`。开发任务只有上一轮已看过的 `gmail_star_email`。确认集将所有其他任务/变体按 `SHA256(deltadom-outcome-v1/task_id/variant_filename)` 排序，每个环境取最小的一项，共 7 组，各跑正常和干预两种条件、seed 42。不按难度、结果、故障类型或原型适配程度筛选；不会替换不支持的任务。14 回合/分支是小规模可行性检查，不是整个基准成绩，也不足以保证统计显著性。

## 分支与边界

1. Browser Use 0.13.11 原生 Agent：限制为正常网站 UI 工具，桌面文本模型，40 步、每步最多一个动作。保留原生观察、记忆和动作系统。增加 `refresh_page`、以 `finish` 替代终止动作供实验封存；不是未经修改的官方论文配置。
2. 同一 Agent + 简单核对：只增加“重新打开/刷新并核对每个要求，不信 toast”的明确指令，不限制其自主核对和恢复。
3. 开发版同一 Agent + OutcomeVerifier：模型在写操作前声明核对条件与已观察到的站内读取地址；代码执行独立重读、身份检查、逐字段匹配，并在缺少当前匹配记录时拦截成功终止。自动核对不自动重试写操作。模型可能漏列条件，所以匹配不能代替任务评分。
4. 候选 v3 `PresenceVerifier`：模型选择已观察到的结果页链接和每个对象的 2..8 个可见身份文本；程序先确认源页唯一、结果页不存在，执行后重载结果页检查新成员。仅支持记录成员关系，不声称通用表单或多目标任务。准备时的往返读取计 2 动作，核对计 1 动作；全部导航/动作总预算 40。成功声明要求当前匹配记录，不自动重试写操作。v1/v2 的失败保留，确认只运行冻结 v3。
5. agent-browser 0.39.1：真实 CLI snapshot/ref/actions + 相同桌面模型通道、40 动作预算。CLI 的 API-backed chat 模式不接受本次指定的桌面模型通道，因此使用明确记录的脚手架；跨框架比较仅作整体表现，不用于归因核对组件。

统一包括成功声明不能只靠点击/toast 的基本要求。没有弱化对手来制造错误。候选新增的模型条件生成、注册和核对同样占动作预算；初始化与最终裁判不计动作。每个请求最多等待桌面回复 600 秒，每回合最多 2400 秒；这是桌面中继上限，不是论文计时复现。超时、无效输出、框架故障、不支持均保留。模型只能收到任务和浏览器证据；禁止读取源码、任务 YAML、评分器、初末后台状态。mailbox 与 judge 目录分离，模型仅被授权操作 mailbox。

开发首回合的外层消息含有分支/条件名字，属于公开标签的开发试跑；确认回合必须采用不含分支/条件名的目录和外层消息。WorkBuddy 自带的工具调用与上下文可能影响行为，因此不能把中继请求数称为全部 provider 调用数，也不能报不存在的精确费用。ChatGPT Desktop 的三个模型尚未运行，不替换渠道。

## 原型判断

`OutcomeVerifier` 支持显式可见文本、值、布尔勾选状态和少数语义属性；对象身份必须唯一且可见。读取地址必须同源。其他类型可能无法覆盖，明确记为未确认。它不读隐藏属性、后台真值或评分器。重新读到的网页仍可能是缓存/伪造内容，不宣称事务、原子性或服务端提交证明。

主要指标：官方最终成功率、错误修改/不变量惩罚、假成功次数（声明成功但官方失败）、明确放弃/未确认、动作数、模型中继请求数和含中继开销的总耗时。候选不能靠全拒绝取胜。

选择规则：先在开发任务验证端到端管线，再冻结候选源码运行完整固定确认集。如果候选仅减少成功声明、没有提高真实完成率，或不优于简单核对，不判为优势。所有失败保留；不从各版本拼最优成绩。确认集一旦用于诊断，就不再被下一版称为未见确认集。

## 运行

先在独立上游 checkout 构建 7 个前端，用其 Python 环境启动 `breakingweb.app:app`，仅监听 `127.0.0.1:18765`。本实验未修改上游任务、干预、评分代码。pnpm 使用上游声明的 10.15.0 和 frozen lockfile；本机默认 pnpm 11 的配置不兼容失败保留为环境问题。

```sh
PYTHONPATH="$PWD/python" .bench/venv/bin/python benchmarks/outcome_agent.py \
  --dev --task gmail_star_email --condition intervention --arm candidate \
  --output artifacts/benchmarks/outcome-v1/dev-candidate-intervention
```

输出目录必须不存在。桌面模型只处理该目录 `mailbox/pending.json` 指向的请求和回复；原始请求、回复、历史、最终页面和 judge 结果分开保存。源码在回合启动时复制并绑定。前两个开发回合早于源码绑定功能，不能据此当作冻结版本的确认结果。

## 确认运行的停止约束

接受优势必须完成冻结集合，不能用部分结果宣布胜出。可以因候选明确不适用或出现劣势而提前否决；此时完整列出已运行与 not_run，不将剩余任务算失败，也不声称完成全基准。首项按 manifest 顺序是 amazon_browse_category；每项先 clean 再 intervention，分支顺序 native / simple / membership / agent-browser。任何诊断改动都退出本次冻结确认；不从修改前后选最佳结果。

### 基线能力修正（确认前两回合期间）

检查安装版本的 `--help` 发现 agent-browser 提供 select/check/uncheck/press 等能力，而早期中继只开放了点击、输入、滚动和刷新。为避免削弱对照，在其第一条确认回合前补全这些 UI 动作和显式字段读取。此时 r001 已完成、r002 正运行；它们均为 Browser Use，执行路径与候选源码未改变。原冻结文件不覆盖，修正前后 SHA 与时点见 `baseline-amendment.json`，实际 CLI 下拉选择/勾选/填写检查见 `harness-preflight.json`。这是已披露的协议修正，不能声称全套脚手架从初次冻结起毫无变化。

### 桌面中继超时修正

r002 暴露 Browser Use 内层 LLM 默认 90 秒会先于 mailbox 的 600 秒取消请求，`step_timeout=650` 无法覆盖。后续显式设 `llm_timeout=600`，旧回合不改写。r001/r002 和后续回合存在此配置差异，本组只能作为公开所有失败的探索性对比，不能作为正向优势证据；冻结集合没有因为该故障而更换。见 `timeout-amendment.json`。

## 本轮结束状态

v3 在首个冻结正常任务上因自身契约限制失败，停止扩大该候选。链接身份 v4 的修复只在已经使用过的购物任务上开发验证，并补齐同一预选干预的一组四分支探索回合 e001..e004。四个回合源码绑定一致，完整确认集保持未完成。桌面中继外层要求最多处理 40 次请求；工具内部的提取也消耗中继请求，不能把请求数和动作数混为一谈。

e002/e003/e004 与 e001 有交叠运行；每个回合使用独立模型会话、浏览器和网站 session。候选 e003 的桌面重复操作提醒恢复一次，没有添加解题提示，事件单独记录。所有耗时包含桌面传输、等待及资源竞争，不用于推理速度或产品加速结论。

回合结束后的语义审计发现同价并列 SKU 的评分歧义，保留全部原分数但不拿它形成优势结论。完整结果、停止决定、实现修复及其验证边界见 [OUTCOME-RESULTS.md](OUTCOME-RESULTS.md)。
